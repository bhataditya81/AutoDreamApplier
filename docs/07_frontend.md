# Frontend Portal Architecture (`frontend/`)

The User Dashboard and control plane for AutoDreamApplier is heavily powered by a React **Next.js 14 (App Router)** frontend application. 

## 1. Core Purpose
The web application provides users with:
1. Visibility over the Job Match queue generated by the `Job Matcher`.
2. A control surface to trigger the `Apply Engine` via HTTP (Accept/Reject workflows).
3. A continuous timeline of their current Applications state (e.g. `Applied`, `Failed`) providing transparent reporting of the background robotics.
4. Preference management editing forms.

## 2. Server-Side vs Client-Side Boundaries
AutoDreamApplier fully dictates the Next.js 14 architectural paradigm. 

### Server Components (`React Server Components`)
- Dashboards and high-level routing pages are `async` Server Components.
- Data fetching occurs on the Node backend (not the browser), pulling `/api/v1/matches` natively utilizing secure fetch configurations.
- API endpoints are heavily masked. Passwords and Tokens (Cognito/HS256) reside securely in `httpOnly` secure cookies negotiated upon user-login, meaning the exact API Gateway URL is never directly targeted by the end-user's browser.

### Client Components (`"use client"`)
- Interaction elements such as the explicit `[ Accept ]` and `[ Reject ]` match buttons on job cards.
- Forms utilizing `react-hook-form` to modify the user's career Preferences (Salary, Titles) or upload new raw resumes.

## 3. Asynchronous UX Patterns
Because clicking `[ Accept ]` sets off a multi-minute background AI/Browser sequence, the UI implements an *Optimistic UI* pattern using React hooks.

1. User clicks Accept on a match card.
2. The card is instantly removed from the DOM UI column (Match Queue).
3. A fetch `POST` occurs silently to the Next.js BFF (Backend for Frontend), resolving against the true Go API Gateway.
4. The card is rendered instantly in the "Applications" column with a status of `queued`.
5. The dashboard timeline periodically revalidates (via SSE or polling) to retrieve updated `applications` progress (e.g. visual indicators moving from `queued` -> `prep_in_progress` -> `applying` -> `applied`). 

## 4. Environment Injection 
The frontend expects dynamic variables populated at build/run time to bridge the gap into the overarching container stack:
- `NEXT_PUBLIC_API_URL` -> Directly routing to the deployed `cmd/api-gateway` instance.
- `AUTH_COGNITO_ID` -> Exposing the UI login sequence to the dedicated AWS User Pool.
